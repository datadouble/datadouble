# Decision log and open questions

## Decided

| # | Decision | Rationale |
|---|---|---|
| 1 | Name: **Datadouble** | Describes the job (a realistic stand-in for real data); free on PyPI, npm and GitHub |
| 2 | Pluggable adapters for dump/load, subset, anonymize, verify, storage, replicate | Breadth of engines is a core goal |
| 3 | Minimum systems: PostgreSQL, MySQL, SQL Server, Oracle, Redis, MongoDB, Salesforce | Required coverage |
| 4 | Subsetting is planned up front and pushed down into extract | Sources can be terabytes |
| 5 | All reads in a run share one consistent snapshot where the engine allows | Integrity of filtered tables |
| 6 | JSON in / JSON out is primary; CLI is a thin layer over it | Interfaces cannot drift |
| 7 | Stages write artifacts with manifests; runs are resumable and chainable | Requirement |
| 8 | Native Jailer `.jm` support, plus a converter that fails on schema mismatch | Design in Jailer, run repeatedly in Datadouble |
| 9 | *(How globs match names is amended by decision 128.)* Excludes by schema/table glob | Requirement |
| 10 | `strict: off \| tables \| columns`, default `columns`; removed/changed objects always fail (Amended by decision 130.) | Unknown tables and columns are the usual PII leak |
| 11 | Containers and sample data for every engine; Salesforce via recorded interactions plus an in-memory fake | Local development requirement |
| 12 | One repository, each adapter a separately published package | Adapter interface will change heavily before 1.0 |
| 13 | ~~Repository private during planning~~ (superseded by 31) | Publish when ready |
| 14 | Licence: MIT | Maximum ease of adoption |
| 15 | CI/CD adapters, Tier 1: GitHub Actions, GitLab CI, Jenkins, Argo CD; each tested end to end | Datadouble mostly runs inside other teams' pipelines |
| 16 | Lifecycle split into jobs: build, promote, fetch, provision, release, prune, activate; stages `promote`, `fetch`, `announce` (named `publish` until decision 44); operations `release`, `prune`, `activate` | Jobs run in different environments, on different schedules, with different credentials |
| 17 | Everything up to `verify` runs where `extract` runs; `promote` into an export store is the only production crossing and refuses unverified images; non-production pulls from the export store only | Raw extracts and working databases contain real personal data |
| 18 | CI/CD adapters contain no pipeline logic and never put data artifacts in CI artifact storage | Same reason as the thin CLI; CI storage is often outside production |
| 19 | *(Refined by decision 98.)* `build` refuses to generate or run on vendor-hosted runners | Prevents production data being pulled onto a vendor's machines |
| 20 | `verify` runs after `package`, against a scratch restore of the image | Verifies the artifact that ships, including that it restores |
| 21 | Run outcomes: success, warning, failure; anything that could leak personal data is a failure; no continue-on-error switch | Operators need "fix this soon" without weakening fail-loudly |
| 22 | Images identified by spec, engine, target engine version and generation; addressed through channels; image summaries (called sidecar manifests until decision 45) readable without download | Cheap change detection, rollback, and test channels that can't replace live images |
| 23 | `replicate` supports pool mode (N unclaimed copies, recycled by generation) and on-demand mode; copies are volumes or instances | Large images copy slower than people will wait; small ones suit per-request copies |
| 24 | Agent skills (Agent Skills format) for each job, the spec, and a whole pipeline; shipped in this repository as a Claude Code plugin and plain skill directories | Agents increasingly do pipeline setup; skills make it repeatable |
| 25 | *(Refined by decision 105.)* Skills contain no logic: all files come from `datadouble` commands, and skills never weaken safety settings or handle secrets | Same reason as the thin CLI; an agent must not trade safety for a passing run |
| 26 | This repository is the Claude Code marketplace and the plugin; no separate marketplace repository and no packaging step | Skills stay versioned with the CLI and cannot drift; an org-wide marketplace can later reference this repository by tag |
| 27 | Implementation language: Python | Mature drivers for every target engine and the Faker ecosystem; the JSON interface keeps callers in other languages unaffected |
| 28 | Strict static typing: `mypy --strict` and `pyright` strict in CI, `ruff` with annotation rules; no stringly-typed values | Untyped dicts and magic strings make adapters hard to extend; types catch interface breaks before runtime |
| 29 | Anonymization strategies include engine-native expressions (SQL, MongoDB aggregation, Painless, Lua) as column rules; `after_transform` hooks that rewrite personal data declare the columns they rewrite | Expressions are often the simplest rule, and declaring columns keeps per-column hashes, reports and strict-mode resolution working |
| 30 | Version 1 scope is [the v1 plan](v1-plan.md), replacing the PostgreSQL-first proposal | Prove the core on one engine, then go wide in one long run |
| 31 | Everything is public: this repository, the documentation site, the example repository; the trademark and domain check is not a gate | Openness over caution for an MIT project |
| 32 | Copyright "(c) 2026- Tight Line LLC", MIT licence; every source file carries a copyright line and `SPDX-License-Identifier: MIT` | Clear ownership and licence on every file |
| 33 | Golden images are signed with cosign keyless signing in `build`; `promote` and `fetch` verify the signature | Non-production can check an image came from the production pipeline |
| 34 | Engines add Elasticsearch and OpenSearch, as separate adapters | Their APIs and clients have diverged since the fork |
| 35 | A filesystem engine adapter: selection by `find` expressions, cleanup by shell commands, a mandatory files PII scan | File trees that rows refer to are needed alongside databases and may hold personal data |
| 36 | Salesforce in version 1 works against the in-memory fake; cassettes are recorded later, outside the run, against a development org | The run never holds org credentials |
| 37 | `CHANGELOG.md` in Keep a Changelog format with an `[Unreleased]` section; every user-visible change and every security fix gets an entry; the release script refuses to tag with an empty `[Unreleased]` | Users learn what an upgrade changes, and security-only releases are possible and explained |
| 38 | Until 1.0, all packages are versioned and released together, with one changelog | One release gate and one changelog while the adapter interface is still changing; independent versions can follow once it is stable |
| 39 | Specs are accepted as YAML or JSON, both validated against one JSON Schema generated from the typed models | YAML for people editing by hand, JSON for programs; one schema keeps them identical |
| 40 | Golden image formats `physical` and `logical` are chosen in the spec (`package.formats`, CLI-overridable); omitted means every format the engine supports; an unsupported format fails the plan | Builds stay reproducible from spec and manifest, and no engine silently falls back |
| 41 | One build can produce several images through named groups in the spec; the extract is shared, each group gets its own working database, and all images from a build share a generation; image identity includes the group | Small images that are easy to reason about, plus combined ones, from one snapshot and without merging images later |
| 42 | Jenkins integration is a shared library in v1; a Jenkins plugin is a possible later addition | Avoids a Java plugin build and hosting process until users ask for it |
| 43 | The documentation site is generated from `docs/*.md`, with Design and Project sections live from M0 and Using Datadouble added in M10 | The docs stay the single source of truth, and the public site shows the design before there is software to document |
| 44 | The stage that tells consumers where clones can be accessed, as volumes or connection parameters, is named `announce` (was `publish`), and its adapters are announce adapters | It never writes data, and "publish" read as writing database dumps into targets such as Secrets or Vault |
| 45 | The small file stored next to each image, read by `fetch` without downloading the image, is the **image summary** (was "sidecar manifest") | "Sidecar" suggested a Kubernetes sidecar container |
| 46 | The documentation site is built with Zensical, pinned to an exact version | Material for MkDocs reached end of life on 5 November 2026; Zensical is its MIT-licensed successor from the same team, Python-based, and actively maintained, but still before 1.0 |
| 47 | Development tasks run through `make`; Python tooling runs through `uv`; tests and lint configuration live in the root `pyproject.toml` | One entry point that CI and people share |
| 48 | Python 3.13 is the minimum supported version and the type-checking target; CI runs the unit tests on every later release (3.14 and 3.15 now, new ones added as they come out); the container images run 3.15, and moving them to a new release is a deliberate change, not a Dependabot update | Installs from PyPI work on older CI runners and workstations, the images get the newest interpreter, and the matrix shows which dependencies lag a new release |
| 49 | *(The binaries requirement is superseded by decision 72.)* Working databases are throwaway database servers the engine adapter starts in scratch space, one per image group; for PostgreSQL, a local cluster listening only on a Unix socket. The machine that builds images needs the server binaries of the version images are built for, and the source's extensions | Nothing shared holds personal data, there is no server to provision, and a physical image is simply the stopped server's files |
| 50 | Each format of an image is its own gzip tar archive holding the engine's files and the build manifest; a store holds `<generation>.<format>.tar.gz` per format, `<generation>.summary.json` and `<generation>.verify.json` | Consumers download only the format they use; gzip is in every supported Python; verification runs after packaging, so its report sits beside the archives rather than in them |
| 51 | The nested strategy (A) treats rows reached through a followed child edge as already having their parent, when the reference targets a key; true recursions (cycles, self-references, children pulling in further parents) run with the keys strategy (B) | Otherwise every followed child edge would make A cyclic; both strategies still choose the same rows |
| 52 | Version 1 refuses to anonymize primary or foreign key columns, `drop` on a virtual reference with `when`, and `stub` or `drop` on a reference that leaves its image group (use `null` or `requires:`) | Each needs integrity handling that cannot yet be verified; failing the plan is safer than guessing |
| 53 | A run belongs to a generation; its work directory (`--work`, default `.datadouble`) holds every stage's artifacts and manifests, and `--resume GENERATION` continues it, skipping stages whose input hashes match | Resume needs a stable anchor time and anonymization key; the work directory is production scratch space and never leaves production |
| 54 | Messages from engines and stores name objects, codes and states but never data values; PostgreSQL messages have quoted strings redacted, S3 errors give only the error code | Error messages reach CI logs, which are outside production |
| 55 | The PII scan flags emails, card numbers, US SSNs and formatted phone numbers, except reserved example domains and documentation ranges, which the anonymizer uses for every generated contact value; reports carry counts per column, never values | A report must not repeat the personal data it found, and generated values must not fail their own verification |
| 56 | *(Fixture storage is amended by decision 78.)* The S3 test service is SeaweedFS, in the Compose default group; sample datasets are fetched at image build at a pinned commit and SHA-256 rather than committed (Pagila v4.1.2, PostgreSQL License) | MinIO no longer publishes community images; every integration run covers the S3 adapter; the repository stays small while the data stays pinned |
| 57 | The non-production side is configured in the same spec as the build (`signing`, `trust`, `promote`, `fetch`, `replicate`, `announce`, `prune`), with each adapter given as a one-key mapping like `store` | One file describes an image's whole life; the spec holds no secrets, so non-production can read it |
| 58 | An image is signed with cosign over its summary without the signature field, which names every archive's SHA-256; the Sigstore bundle is stored as `<generation>.sigstore.json`. Keys are passed by reference (`env://` or a path); keyless signing works through the CI system's identity; the transparency log is on unless turned off | The signature covers the image's contents without signing gigabytes, and Datadouble never holds key material |
| 59 | `fetch` skips a generation that is already staged, active or not | A rollback with `activate` holds until a genuinely newer image is promoted, instead of being undone by the next scheduled fetch |
| 60 | Outside Kubernetes, consumers take a pool copy with `datadouble claim --owner`; replicate adapters that can see claims themselves report them (a bound PersistentVolume is claimed, a released one returned and removed) | Pool mode needs a claim step everywhere; Kubernetes already has one |
| 61 | `k8s-pv` is a replicate adapter: each copy is a directory and a PersistentVolume, and the volume, with its labels, is also the announcement; there is no separate `k8s-pv` announce adapter | Creating the volume is what makes the copy usable on Kubernetes, and its phase is how claims are seen |
| 62 | Instance copies run the engine's server in a container on a volume copy, as the engine adapter describes it (`ServerPlan`); each copy gets a generated password, passed through the environment rather than a command line, and only `dotenv`, `k8s-secret` and `vault` receive credentials | Any engine can be served without the replicate adapter knowing about it; copy credentials stay out of job outputs and process lists |
| 63 | btrfs copies are subvolumes filled with reflinked copies of the staged image, not snapshots of a base subvolume | Copies are as cheap as snapshots, the adapter keeps no state, and staging stays plain directories |
| 64 | *(The Compose default group and Docker-in-Docker in CI are amended by decision 88.)* Docker-in-Docker and OpenBao join the Compose default group; k3s (`k8s`) and a loop-mounted btrfs (`btrfs`) are opt-in groups that need privileged containers, each with its own CI job; cosign, kubectl and the Docker CLI are pinned in the test image, and stand-in scripts let unit tests cover the code that drives them | Real tools prove the behavior; the stand-ins keep coverage complete on any machine |
| 65 | A MongoDB collection is a table and a dotted field path a column; columns come from a sample of documents (`sample`, default 1000) merged with any `$jsonSchema` validator; sampled fields are nullable except `_id`, and a field seen with several BSON types has kind `other` | MongoDB has no schema to read; a validator is the closest thing to one, and sampling finds what it leaves out, so strict mode still sees every field in use |
| 66 | MongoDB extract reads inside one snapshot session (`snapshot: true`), and needs a replica set or sharded cluster; collection and index listings run outside the session, which they do not support, and the catalog fingerprint is compared again inside it | A snapshot session is MongoDB's consistent point-in-time read; checking the fingerprint catches a schema change between the listing and the reads |
| 67 | Seeds, `when` clauses and `where` conditions for MongoDB are query filters in Extended JSON, with `":as_of"` standing for the plan's anchor time; an `expression` rule is an aggregation expression, and an assertion is `{"collection": ..., "pipeline": [...]}` whose result documents are failures | Each piece is MongoDB's own language, as SQL is for the relational engines, and the anchor time keeps seeds stable across resumes |
| 68 | Engines declare in their capabilities whether they run hooks; MongoDB runs neither hooks nor the nested strategy (A), so it builds with the keys strategy (B) and plans with hooks fail | MongoDB cannot evaluate another collection's selection inside a query, and a script language for hooks would be a second, unverified anonymizer |
| 69 | The test image runs MongoDB's own Debian 13 server and database-tools tarballs, pinned by version and SHA-256; the Compose `mongodb` service is a one-member replica set seeded with a generated cinema database | MongoDB's apt repository lags new releases; the tarballs run on older x86-64 CPUs where the packaged tools do not; generating the data keeps its licence clear |
| 70 | A hash replacement that the PII scan would flag (a hex digest can hold a Luhn-valid digit run) is retried with the next attempt | A hash must never fail its own image's verification |
| 71 | *(Where its coverage comes from is amended by decision 88.)* The SonarCloud quality gate is enforced by the required `sonar` job: the scan waits for the gate (`sonar.qualitygate.wait`) and fails the job when the gate fails. Coverage roots are `src` directories, and `scripts/check_coverage.py` fails the job if the report names any analysed file more than once or not at all | A red gate must block a merge; Dependabot pull requests run without the Sonar token, so requiring the SonarCloud app's own check would block them; a report keyed by package-relative names (`__init__.py`) silently merged files and scored them as uncovered |
| 72 | Engine software runs in the engine vendor's container images, never beside Datadouble: working databases, restores for verification and tools such as `pg_dump` and `mongorestore`. The published `datadouble` image carries Datadouble, its adapters, the `docker` command, `kubectl` and cosign, and no engine software. Supersedes decision 49's requirement that the build machine hold server binaries | Engine binaries tied Datadouble to one host's packages and versions, and SQL Server and Oracle ship only as images in practice; the vendor's image matches the source's version and carries its own tools |

| 74 | Working servers accept a password generated per start, passed through the runtime's secret channel (the `docker` command's environment, or a Secret object made for the pod); tools that need a working server run inside its container. | 77 | External programs run only through `datadouble.programs` (no shell, arguments as a list), which holds the repository's one subprocess suppression; the number of checker suppressions must equal a budget in `pyproject.toml`, so adding one raises the budget in review and removing one lowers it | Suppressions had grown with every adapter that wraps a tool, mostly the same subprocess rule repeated; a budget makes each new one a visible decision and lets the count only ratchet down otherwise |
| 78 | Test fixtures are committed and constant. Sakila, the sample data for MySQL, SQL Server and Oracle, comes from jOOQ's collection (commit `e089a5b1`), which has it for every relational engine. Each engine's schema still comes from the same collection at that commit. Amends decision 56, and replaces AdventureWorks and the HR/SH schemas in the v1 plan | Tests need data that never changes; one dataset across the relational engines makes their results comparable and matches Jailer's Demo-Sakila model; Sakila's insert scripts took 13 minutes to load where the bulk files take seconds, and keeping the data out of images keeps it out of everything that is built and published |
| 79 | *(The catalog is amended by decision 128.)* The MySQL adapter's catalog is the URL's database. Keys and rows are read in one `START TRANSACTION WITH CONSISTENT SNAPSHOT` connection, rows unconverted in `LOAD DATA`'s text format; `mysqldump` writes the schema and, separately, the triggers, with `DEFINER` clauses removed, and the catalog fingerprint is checked inside the snapshot. Load runs the schema, `LOAD DATA` with foreign-key checks off, the fallbacks, then the triggers; transform sets triggers aside and keeps `ON UPDATE` columns, since MySQL can switch neither off per session. Tools in a working server's container connect as `root` over its socket; a build user with a per-start password serves Datadouble and is dropped before the server stops. All SQL is composed in one helper from quoted identifiers, placeholders and spec SQL | MySQL has no exported snapshots, versioned catalog or session switch for triggers, so each is handled where it arises; the vendor's own text format round-trips every type without conversion in Python |
| 80 | Milestone 4 is five pull requests: container runtimes (done), MySQL, the Jailer front end with its Sakila key-set comparison, SQL Server, Oracle. Amends decision 76 | Each engine and the Jailer front end are large enough to review on their own, and each stays green |
| 81 | Jailer subsets are a spec's `subset.jailer` (model and data model), translated against the live catalog at plan time, or imported once as native settings with `import-jailer`. Restriction conditions, non-equality joins, subject limits, parameters and column filters fail the plan by name in version 1 | Running a subset different from the one designed would be worse than refusing; the translated features cover the Sakila model the milestone compares, and each missing one needs a native equivalent first |
| 82 | Every CI job sets `timeout-minutes`, a few times its normal run, enforced by `scripts/check_workflows.py` in `make lint-workflows`; every test fails after 10 minutes with its stack (`pytest-timeout`) | A runner that stopped responding held a pull request's checks pending for over two hours under GitHub's six-hour default, with no log to show why |
| 83 | SQL Server working databases run in Microsoft's `mcr.microsoft.com/mssql/server` image of the source's release and cumulative update (`2022-CU28-ubuntu-22.04`, from `SERVERPROPERTY`), and the build must match the source's; a source on a security update (GDR) names its image in `source.image`. | 84 | The SQL Server source must allow snapshot isolation; extract reads keys, the schema and rows in one `SNAPSHOT` transaction and runs nothing in a container. | 85 | The SQL Server adapter scripts the schema from the catalog views in phases (schemas and sequences; tables with keys, defaults and identity; then indexes and checks, foreign keys, modules in dependency order, triggers), each statement recording the table and objects it needs, so a group's database leaves out what refers to tables it lacks. | 86 | Each engine adapter declares the `uid:gid` a copy of its images is served as in its vendor's image (`owner`): 999:999 for the official PostgreSQL, MySQL, MongoDB and Redis images, 1000:0 for Elasticsearch, 1000:1000 for OpenSearch, 10001:10001 for SQL Server, 54321:54321 for Oracle. Datadouble runs as exactly that user and group to build, fetch and replicate the engine's images, and refuses otherwise, so a physical image's files belong from the start to the server that will open them and no copy needs its ownership changed. Datadouble's image works under any uid; the integration suite runs each engine's tests as its owner and combines their coverage. Amends decisions 73 and 83 | The engine and Datadouble share every file they hand each other, and the engines create theirs readable only by their owner; SQL Server and Oracle run only as their own users; and a `btrfs` or `k8s-pv` copy keeps the owner it was built with, so a physical image built as anyone else could not be served |
| 87 | The Oracle adapter's catalog is the connection's `schemas` (the connecting user's own by default). `DBMS_METADATA` scripts the schemas just before a `READ ONLY` transaction reads keys and rows, and the catalog is checked inside it; values are converted by the server to text it reads back exactly. | 88 | The integration suite runs in groups (`tests/integration-groups.txt`), each with its own user, Compose services and test paths, and each its own CI job in parallel; `make test-group` runs one and `make test-integration` all of them. | 89 | A slow integration group is split into shards (`tests/integration-groups.txt` sets how many), each its own CI job: shard K of N runs every Nth test in collection order, starting with the Kth (`pytest --shard K/N`, `scripts/shard.py`), and CI's job matrix is read from the table. pytest keeps only failed tests' temporary directories, and `DOCKER=host` runs keep theirs in `/var/tmp/datadouble-work`, which `make clean-work` and the next run empty. Locally, groups run whole; before a push, only the groups of the engines that changed need running. Amends decision 88 | Sharding divides a slow group's time without changing what the tests run or how Datadouble starts engines, which reusing engine containers would; each shard pays the job's two minutes of setup again, so only groups whose tests take several minutes get more than one; interleaving spreads a file's slow tests across shards with no recorded timings to maintain. | 90 | Shards are balanced by the seconds each test took in CI (`tests/integration-durations.json`): longest first, each to the shard with the least time so far, with unlisted tests counted as the average. Every integration job records its tests' durations, and the coverage job merges them into an artifact, which is committed by hand when the shards drift apart. Amends decision 89 | Round-robin put Oracle's longest tests (whole builds, the two-strategy comparison) in the same two of six shards, which took 26 minutes against 8 to 13 for the rest; durations change only when tests do, so a committed file is enough, and a stale one only unbalances the shards, never skips or repeats a test |
| 91 | Working databases keep each engine's default sizes: physical images carry the engine's fixed overhead (73 to 211 MB unpacked for PostgreSQL, SQL Server, MySQL and MongoDB, 873 MB for Oracle's pluggable database), recorded in `TESTING.md` from every CI run's `image-sizes` artifact. | 92 | M5 is three pull requests: Redis, then Elasticsearch, then OpenSearch | One engine per pull request kept M4's reviews and CI runs small (decision 80) |
| 93 | The Redis adapter's tables are key patterns in each database (`db0`, `db1`…), with ID-like key segments written `{}` (`user:{}:sessions`) and declarable patterns for the rest; `_key` holds the values the placeholders stand for and is the key, and the other columns are what the keys hold (`value`, hash and stream fields, `members`, `scores`).
